# ADR-0054: Raw HTTP is the untyped tier of service-to-service connections

## Decision

`@prisma/composer/http` ships `rawHttp()` and `rawHttpContract`: a
service-to-service connection whose only promise is that the provider answers
HTTP. The provider declares the port; the consumer declares the dependency; the
module wires one to the other, exactly like any other connection.

```ts
import { module } from '@prisma/composer';
import { rawHttp, rawHttpContract } from '@prisma/composer/http';
import node from '@prisma/composer/node';
import { compute } from '@prisma/composer-prisma-cloud';

const docs = compute({
  name: 'docs', deps: {}, expose: { http: rawHttpContract },
  build: node({ module: import.meta.url, entry: 'server.js' }),
});
const gateway = compute({
  name: 'gateway', deps: { docs: rawHttp() },
  build: node({ module: import.meta.url, entry: 'server.js' }),
});

export default module('web', ({ provision }) => {
  const docsRef = provision(docs);
  provision(gateway, { deps: { docs: docsRef.http } });
});

// in the gateway's server
const { docs } = gateway.load();   // { url, fetch(path, init) }
```

The contract's kind is `http`. It compares by kind only, so any port declared
with `rawHttpContract` fills any `rawHttp()` slot. The name `http(contract)` is
reserved for a typed tier that describes routes.

## Reasoning

Postgres already has two tiers. `rawPostgres()` says "I need something that
speaks Postgres; trust whoever wires me". The ORM-typed `postgres(contract)`
says "I need a database that satisfies this schema", and the framework checks
it. Service-to-service connections had only the typed tier, service RPC, which
works because the framework generates both the client and the server. Many
servers are not generated by the framework: a reverse proxy's upstreams, a
Next.js app, a static file server, Better Auth's browser endpoints. Before this
decision, an app that called one of them had two bad options. It could pass the
URL as configuration, which declares no connection, so the topology loses the
edge. Or it could use the untyped `http({ name })` slot, which accepted any
provisioned reference, a database included.

`rawHttp()` is the raw tier for these servers. The consumer takes on the
burden of knowing which paths, methods and headers the provider accepts. The
framework checks only what it can: that the provider declared an HTTP port.

**The provider declares the port.** Every Prisma Compute service answers HTTP,
but that is a fact about one platform, and another target may differ. More
importantly, a service that has no intention of answering on HTTP should not
appear to offer it. The declaration states intent.

**It lives in the target-agnostic core.** An HTTP connection is a protocol
between two services, like service RPC, not a resource that a target
provisions, like a database. The deploy target only supplies the provider's
URL, which every compute service already publishes to its consumers.

**There is no service key, retry or idempotency.** Service RPC gets those
because the framework generates the server that checks them. A raw HTTP
provider is the app's own server, so the framework cannot enforce anything on
the far end. Authentication, if the provider wants it, is the app's concern.

**Contracts describe interfaces, not providers.** The auth module used to
expose Better Auth's endpoints under its own kind, `auth-api`, which was a raw
HTTP contract with a different label. A label named after the provider makes
connections non-interchangeable for no reason: a test double or an alternative
auth server could only fill the slot by claiming to be the auth module. That
port is now a `rawHttpContract` port. A typed HTTP tier can later describe
Better Auth's routes as an interface that any implementation satisfies.

**A contract declares its own communication style.** The `Contract` type gains
an optional `style`: `request-response` or `stream`. Service RPC declares
`request-response`. Raw HTTP declares none, because an arbitrary HTTP server
may do either. The application topology reads the style from the producing
port's contract instead of keeping a list of kind names in the deploy target.

## Consequences

- A gateway can declare each upstream as a dependency. The topology then shows
  the gateway calling each upstream as a communication edge with no style.
- The untyped `http({ name })` in `@prisma/composer-prisma-cloud` is removed,
  and with it the last slot that accepted any provisioned reference.
- `authApi()` and the `auth-api` kind are removed. A consumer of the auth
  module's `api` port declares `rawHttp()`. `jwtVerifier()` requires
  `rawHttpContract`.
- Edges that previously had no style because their kind was missing from a
  list now take the style their contract declares.
- The intended design is that a more specific HTTP kind, such as service RPC,
  also fills a raw HTTP slot, since a raw consumer already knows what the
  provider accepts. That is not built. Contract kinds have no parent kinds, and
  TypeScript compares kind names exactly. Building it means teaching
  `Contract` about a parent kind. A consumer wired that way would also need to
  send the RPC service key itself; that is the consumer's knowledge to hold,
  like everything else a raw slot asks of it.

## Alternatives considered

- **Every compute service offers an HTTP port automatically.** It is always true
  on Prisma Compute, so the declaration looks like ceremony. Rejected: other
  targets may differ, and a service that does not intend to answer HTTP should
  not appear to.
- **Keep the kind in the Prisma Cloud package**, beside `rawPostgres()`.
  Rejected: a database is something a target provisions, but HTTP is a protocol
  between services, the same category as service RPC.
- **Overload one name**, with `http()` for raw and `http(contract)` for typed.
  Rejected: one name would mean two different checks. The Postgres tiers
  already use `raw` for the untyped one.
- **Model the gateway as the only public entrypoint.** Every Prisma Compute
  service is reachable from the Internet; that is how the platform works, and
  a topology that claimed otherwise would be wrong. This decision records the
  calls services make, not their exposure.
- **Keep `auth-api` as its own kind.** Rejected for the reason above: it names
  a provider, not an interface.
- **Add `http` to the deploy target's list of request/response kinds.** One
  line, but every new kind would have to remember to add itself, and raw HTTP
  is not necessarily request/response.
