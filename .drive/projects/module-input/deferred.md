# Deferred

- S10: an object field with a `field()` leaf (for example `input.smtp` with a wrapped `user`) does not compile as a service binding, because `Pointer<string>` is not accepted as `InputBindingData`. Pre-existing. Closed in S10: `InputBinding<T>` maps the field's type, and `field.test-d.ts` passes `input.smtp` into a service's binding in both libraries.
- S10: check the docs' claim that a field may be a whole service binding (`input: input.smtp`) once service bindings are typed from schemas. Closed in S10: the claim holds; type test 7 of the S10 spec compiles it, and runtime tests 9 and 12 show Load and the serializer handle it.
- S10: a service binding of the whole input fails to compile with "ServiceNode is not assignable to ModuleNode" instead of the message. Closed in S10: the last `provision()` overload is generic over services and modules, so the error shows the message (§ 8 of the S10 spec).
- S10: a service or module that declares both dependencies and an input schema, provisioned with `deps` but without `input`, compiles, because the overload kept for generic wrappers takes `input` as optional. Load refuses it. Pre-existing; found in S10. Closed in S10: each overload with `deps` written out is split into one that requires `input` and one, for a node without an input schema, that refuses it; `field.test-d.ts` refuses the call for a service and a module.
- Later: `module()` does not refuse an input schema whose output is not an object. Refusing it would be a new constraint the design does not ask for.
- Later: `InputRef` (the type of a dependency a module body forwards) and `ModuleOutputs` (one port per exposed interface) use "input" and "output" for the ends of a connection, the sense ADR-0063 retired. They sit in `@prisma/composer`'s exports beside `InputBinding`, `InputBindingOf`, `InputValueOf` and `ModuleInput`, which use "input" for the document a node declares. Rename them after ADR-0063's words, for example `DepRef` and `ExposedPorts`. Found in the S10 review.
- Later: a service wrapper generic only in `I`, with no dependencies, that does not widen the node, cannot call `provision(s, { input })`. TypeScript defers the conditional on an unbound `I` and refuses the call. Pre-existing (it failed before S9 as well). Widening the node to `ServiceNode<D, P, E>` works around it, as `module-composition.md` documents. Found in the S10 round-2 review.
- Later: an app that installs a different `@prisma/composer` version from the one `@prisma/composer-prisma-cloud` pins exactly gets a second, nested copy. `SecretBox` and the node brand then split again, and a redacted `generatedParam()` no longer fits a `secretString()` field. Pre-existing and not specific to S10's fix. Found in the S10 round-2 review.
- Later: `@prisma/composer-prisma-cloud`'s published JavaScript still inlines some foundation code: `describeKind` from `@internal/foundation/errors` (no public entry exports it), and `blindCast`, `field` and the secret and pointer helpers inside the `testing` entries and `local-target`, which come from internal packages' prebuilt `dist`. Each reads `Symbol.for` brands or is a plain function, so behavior matches, and no foundation type is inlined in the declarations. Found while fixing D16 of the S10 round-2 review.
- Later: two redaction markers reach the user. `SecretString` and `SecretBox` print `[REDACTED]`; the CLI's redactor prints `[redacted]`. Pick one. Pre-existing; found in the S11 to S13 design review.
- Later: Composer's variables use two prefixes: `COMPOSER_` on the platform variables a deployment sets (ADR-0029), and `PRISMA_COMPOSER_` on the variables Composer's processes read. Pick one, or record why both stay. Pre-existing; found in the S11 to S13 design review.
- Known limit: `destroy` runs only the `config` adapters, not the `secrets` adapters (Will's ruling: an unreachable secrets manager must not block a teardown). So on `destroy`, which reads no secrets, a secret only the `secrets` list returns is not known, and the file check cannot refuse it. Destroy still compares against a value under an `envSecret()` name in the app configuration, and Load still refuses a root field named like an `envSecret()`. A deploy of the same configuration refuses first, so the impact is small. Found in the S11 to S13 round-2 code review (F11); still open after round 4 (F22).
- Known limit: the stream redactor's cost grows with the square of the longest secret's length. Only programmatic hosts use it, through `spawnAlchemy`. It matters only for secrets of many kilobytes, such as a CA bundle in a credential-named variable: a 32,000-character secret costs about 2 seconds per megabyte of output. A trie or rolling hash would make it linear. Found in the S11 to S13 round-2 code review (F12).
- Shelved by Will, 2026-11-05: a command that seeds platform values from the app configuration and the app secrets (`.env`, the shell). From the platform-variables project's slice P3, `deploy` never does it; until then deploy preflight fills a missing `envSecret()` variable from the app secrets.
- Deferred to the in-process Alchemy work: redacting the second process's (Alchemy's) output. Will dropped the engine change it needed (`@prisma/cli-engine` piping a child's output, prisma/prisma-cli#383) on 2026-11-05, because the Alchemy integration moves to the programmatic API soon. That work must redact Alchemy's output itself: in Composer's own process, Alchemy writes to Composer's output, and nothing redacts it unless the integration routes it through the command's `SecretRedaction`. Until then Alchemy's output prints unredacted under the CLI, as before S13. A programmatic host's `spawnAlchemy` does redact it.
- Known limit: Nothing is redacted by the known secrets before Load has named them: an adapter that throws, and a root schema failure that echoes a field's value, are redacted only by the credential-looking rule. A fix needs the secret names before Load, which the design does not provide. Found in the S11 to S13 round-4 reviews (F20).
