# Deferred

- **A start can join a crash-backoff restart that has already exited (prisma/composer#353).** When the fifth fast exit marks an instance `held`, the readiness probe only notices the exit after its current connection attempt. A start request arriving in that gap joins the dying start and gets its old failure, so nothing resumes. Seen once as an intermittent failure of "a held service resumes on start" in `compute-deployment.test.ts`; not reproduced in 10 runs under CPU load. Likely fix: a start must not join an in-flight start whose process has already exited. Belongs in #353, not this project.
- **What a previous app's databases and buckets become when another app runs from the same directory.** Compute instances are deleted (S1a). Databases and buckets hold data; decide in S1b.
- **`[dev]` notices bypass the CLI engine's output.** The emulators hook writes `[dev] compute emulator ready`, the port-change line and the app-switch line with `console.log` to stdout, so once a pipe gets plain data (prisma-cli's piped-output change) they land among a piped `prisma dev`'s data lines; with `--json` they still mix into the JSON frames. Fixing it needs a channel for the local target's hooks to report through the engine.
- **A deployment that arrives while its instance is being deleted can start a process the emulator no longer tracks.** Same race as #353's app delete.
- **`env.json` and `secrets.json` in `.prisma-composer/dev/` are shared by every app run from a directory, and `--fresh` wipes them.** One app's `--fresh` can drop rows another app in the same directory needs on its next redeploy. Pre-existing. Making them per app, like bucket objects (S1b moved those to `buckets/<app>/<bucket>/`), would fix it.
- **A service that never listens fails `prisma dev` under prisma/composer#353** (the cron scheduler; `examples/store`). Raised with Will; the fix belongs in #353.
- **`prisma dev url` doesn't retry an emulator that is briefly unreachable.** Retry policy is #353's (`withEmulatorRetry`); apply it here once that settles.
- **`prisma dev url` loads the config's extensions, and so Alchemy, to read one JSON file.** It only matters when a script calls it in a loop.
- **A run-then-stop mode for CI: `prisma dev --exec "<cmd>"`, like Firebase `emulators:exec`.** It would bring the app up as `--detach` does, run the command, stop the app and exit with the command's code. Likely next step after S6.
- **Commands that print nothing to a pipe once prisma-cli's piped output becomes plain data.** Each needs data lines in its owning repo:
  - Composer `prisma deploy`: the deployed addresses (and URLs where public), one per line.
  - ORM (`@prisma/orm-toolchain`): `migration list` and `migration ref list` (one row per item), `migration status` (`key<TAB>value`), `migration log`, `migration show`, `migration plan` and `migration new` (the created migration's id or path), `migration check`, `migration graph`, `migration ref set` and `migration ref delete`, `contract infer`, `contract format`, `contract print` (the printed contract is the data), `db init`, `db schema`, `db sign`, `db update`, `db verify`, `db migrate`, `orm init`. Matched by function name in the built bundle, so approximate.
