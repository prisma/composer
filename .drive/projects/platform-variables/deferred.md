# Platform variables: deferred

Items this project does not do, and why.

## Waiting on the platform

Each needs a Management API change. None blocks this project (design section 3).

- **A platform record of which variables each service reads.** Composer's input documents already name them; the target would also send them to the platform, which could then deliver only those. Until then every deployment receives every row of its class.
- **A service scope.** Today a name resolves at two scopes, project class and branch, and preflight lists both. Will expects the platform to add a service scope. When it does, preflight's existence check gains one list call per reader; nothing else in the deploy changes, because the node never says where its value lives and preflight is the only part of the deploy that knows which scopes exist. `prisma dev` supplies one value per name from local files, so reproducing two readers with two values locally needs a per-reader local source, decided when the scope exists.
- **A void value.** Let an operator set a variable to "deliberately nothing", so the deploy report stops listing an intended absence as not set. Today the platform refuses an empty value.
- **Workspace variables and rules.** Values shared across projects, with rules for which branches see them. Composer does not create platform variable values today, so this needs nothing from Composer.
- **A topology entry for a platform variable node.** The platform's application topology has a fixed list of node kinds, owned by the Portal team. The node is not sent to it until the platform has a kind for it.

## Later Composer work

- **Destroying production deletes the operator's platform variables.** Destroying an app's production environment deletes its Prisma Cloud project, and with it every variable the operator set; the platform never returns a value, so an operator who kept no copy must make a new secret. Options: keep the project when it holds rows that are not Composer's, or warn before deleting. Waits because destroy's behaviour is not this slice's and needs its own decision.
- **An author-declared per-reader variable,** one that maps to the service scope the platform is expected to add, so that two readers of one name are guaranteed different values. Not built: where a value lives is the operator's choice on the platform, and nobody has a case that needs the author to force it. Wait for a real case.
- **A warning when the app names a variable another module expects under a different name.** Not needed: the deploy report lists every name with its readers, so a module wired to the wrong name shows up there.
- **An edge kind for "a service reads a platform variable".** Core's edges are dependencies (ADR-0063 names two relationships: depends on, exposes). The reads relation is recorded as one list on the graph, `Graph.valueReads`, not as an edge, because adding an edge kind changes core's graph types and the platform's edge families at once. Reason to wait: nothing reads the relation as an edge yet; the deploy report and errors read the list.
- **`schema` on a platform secret.** A secret box whose content is not text is undefined in this design and in module-input's. A `secret(inner)` field already checks a secret's text at boot. Needs a generic box type first.
- **An explicit way to set platform variables through `deploy`.** The operator names the values and the environments they go to, and the deploy writes those rows. Expected later. Not now: it needs its own design, and an implicit copy of local values is what slice 2 removed.
- **Isolating a service's environment on Prisma Cloud** without a platform record of who reads what, for example by having boot remove variables a service does not read. Not planned: it would hide variables an app reads directly from `process.env`.
- **Reading a deployment's logs from `prisma deploy`.** Composer does not tail deployment logs, so a boot error on the platform is read with `prisma service logs <service>`. The guide says so; tailing is a later change.
- **A value given by a resource that also provides a contract.** A value resource holds its value under a core-only key, so the node itself has no clash. The conflict is the return of `provision()`, which would have to carry both the contract's ports and the value. Allowed only on a resource with no contract until a second case needs both.
- **A report channel for preflight checks that are not about platform variables.** `PreflightInput.report` carries platform-variable findings and a count only. Designing a general channel waits for a second preflight check that needs one.
- **The CI script's deep imports from source paths.** `scripts/e2e-first-deploy.ts` imports from `packages/1-prisma-cloud/0-lowering/lowering/src/`, as four other scripts already do. Changing it is a change to that existing practice, not to this project.
- **The platform variables with no value in the `--report` run report.** The printed deploy report and the JSON output carry the list; the run report file holds steps, timings and the failure cause, and does not. Found in slice 2 QA. Reason to wait: no CI consumer reads the list from that file yet.
- **Moving Prisma's other repositories off `envSecret()` and `envParam()`.** Slice 3 removes both. Internal apps call them: the deploy apps in `prisma/streams`, and the apps in `prisma/asks`, `prisma/program` and `prisma/pdp-control-plane`. `prisma/skills` and `prisma/web` document them. Each moves in its own repository when it upgrades Composer, following slice 3's migration guide.
- **The service's own schema can quote a plain platform variable's value at boot.** When the service's schema refuses its input, boot prints the schema library's message, which can quote the value a plain platform variable filled, and with object values one of its keys: ArkType's `cfg["<key>"] must be removed` or `cfg.url must be a URL string (was "<value>")`, Zod's `Unrecognized key: "<key>"`. A platform secret is boxed and never printed. The service-input decision record says errors about a binding's data are the schema library's own messages. Replacing the message for the paths a plain variable filled would reverse that, so it needs its own decision. Reason to wait: it is a design question for the owner, and the value case existed for text variables before slice 4.
- **An author's `pattern` or `uniqueItems` can make boot slow on a hostile or large value.** The validator runs `pattern` and `patternProperties` with the engine's backtracking matcher: with `^(a+)+$` and a 29-character text, one validation took 20 seconds on Node and 0.6 seconds on Bun, and each extra character doubles the time. `uniqueItems` compares every pair of items: a 100 KB array took 1.2 seconds on Bun. The constructor only checks that a pattern compiles. Reason to wait: bounding either needs a matcher without backtracking or a limit on a value's size, which the platform does not record, and the author writes the pattern.
- **Inlined third-party code ships without a notices file.** `@prisma/composer-prisma-cloud` and the shared modules inline `@cfworker/json-schema` (MIT), as they already inline ArkType, `@standard-schema/spec`, `fastq` and `reusify`, without their copyright notices, and the published package carries no notices file. Reason to wait: it is a repository-wide matter, for example a third-party notices file built from the inlined packages' licences.
- **A node constructor's refusal is reported as Composer's own error.** A refusal thrown when the root's body runs, such as a schema `variable()` cannot read or a reserved name, reaches the user with the code `CLI.INTERNAL_ERROR`, which blames the tool for the author's mistake. Found in slice 4 QA; true since slice 3. Reason to wait: it belongs to how the CLI classifies errors thrown during Load, a change of its own.
- **Running the dev preflight on every rebuild.** Today `prisma dev` works out the values and the unset variables once, at start, so a rebuild that changes which platform variables the services read pauses rebuilds until `prisma dev` is restarted. Running the dev preflight on every rebuild would apply such a change without a restart. Reason to wait: it is a separate change to the dev loop.
- **A root input field the root's body never passes on escapes the one-meaning check.** The graph check's refusal of a plain platform variable node and a root input field with one name, and core's refusal of a platform secret and a root input field with one name, see only the root input fields the root's body passes on to a binding. Composer lists no root schema's fields today. The service-input decision record ([ADR-0042](../../../docs/design/90-decisions/ADR-0042-service-input-is-one-standard-schema.md)) says Composer never looks inside a library's schema, but Standard JSON Schema now offers a public way to read a schema's fields, the one slice 4 uses for a platform variable's schema, so the fields could be listed through it for a library that implements it. Such a field reaches no service, so no service reads the name two ways. Reason to wait: no app has needed it, and a library that implements only Standard Schema would still not be covered.
- **A rebuild under `prisma dev` loads the app's modules as they were at start.** The first process loads the entry again with `import()`, and the runtime returns the module it already loaded. So after an edit to `module.ts`, the first process's graph is the old one: the check that pauses rebuilds when the app's platform variable reads change sees no change, and an edit that adds or removes any node fails the converge with "the second process built a different graph", whose advice does not fit. This affects every edit to the graph under `prisma dev`, and was found in slice 3. Reason to wait: loading the edited modules needs a fresh module graph on each rebuild, which is a change to the dev loop with its own design.
- **The local dev server path reads the whole app configuration for a service's variables.** The local target's `materializeEnv` takes the plain platform variable texts for a deployment, and the whole app configuration when a build adapter's dev server is started (`serve`). Both give the same value for a variable the dev preflight accepted. Giving `serve` the start-time texts would make the two the same, but it changes core's `serve` contract. Reason to wait: no behaviour differs today.
- **Where a compute service's port is set.** A compute service declares one per-key param, the reserved `port`, and the deploy reads its number to set the deployment's port mapping before the service exists. Whether the port should be set through a per-key param at all, or somewhere else such as the build options, is not decided. Reason to wait: it is a question about the compute service's design, not about platform variables.
- **Renaming core's `ParamSource` and `paramSource()`.** A per-key param takes no source, so the names now describe a source that no param accepts; it is the plain sibling of a secret source, and a name such as "plain source" would say so. Reason to wait: it is a rename across core's extension interface, `generatedParam()`, `serviceOrigin()` and the glossary, separate from this slice.
